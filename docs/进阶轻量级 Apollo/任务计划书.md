# GoLiteConfig 进阶轻量级 Apollo 任务计划书

## 1. 项目背景

当前 `GoLiteConfig` 已具备轻量配置中心的基础能力：

- 支持配置发布
- 支持当前版本查询
- 支持历史版本管理
- 支持回滚
- 支持基于长轮询的配置监听
- 提供基础 Go SDK

下一阶段目标不是重做一套新系统，而是在现有能力上继续演进，使项目从“轻量配置中心”升级为“进阶轻量级 Apollo”，补齐更接近 Apollo 的核心体验，同时保持架构简单、实现轻量、便于答辩和演示。

## 2. 项目目标

本阶段目标如下：

1. 将配置模型从 `app + env` 升级为 `app + env + namespace`。
2. 支持更完整的发布元数据与版本管理能力。
3. 补齐配置对比、审计预留、删除策略等关键能力。
4. 增强 SDK 的本地缓存、容错与热更新体验。
5. 为后续最小控制台打好接口与模型基础。

## 3. 建设原则

- 轻量优先：继续采用 `Go + Gin + Etcd`，不引入过重中间件。
- 渐进演进：尽量基于当前 `service / handler / sdk` 结构升级，而不是推倒重来。
- 演示导向：优先实现可展示、可验收、可讲解的主链路。
- 兼容优先：新设计尽量兼容当前模型，必要时提供迁移方案。

## 4. 核心演进方向

### 4.1 配置维度升级

从当前：

```text
/config/{app}/{env}/...
```

升级为：

```text
/config/{app}/{env}/{namespace}/...
```

其中：

- `app` 表示应用名
- `env` 表示环境
- `namespace` 表示命名空间，如 `application`、`database`、`redis`

### 4.2 元数据升级

发布元数据在现有 `version / revision / publisher / comment / created_at` 基础上，补充：

- `namespace`
- `release_title`
- `release_type`
- `operator`
- `source_version`
- `format`

### 4.3 接口能力升级

围绕现有接口，逐步扩展：

1. 发布接口支持 namespace
2. 查询接口支持 namespace
3. 版本历史支持 namespace 维度查询
4. 新增版本 diff 接口
5. 为审计日志保留模型和接口扩展位

### 4.4 SDK 能力升级

SDK 后续重点增强：

1. 多 namespace 加载
2. 本地缓存
3. 容错降级
4. 强化 onChange 回调
5. typed API

## 5. 任务分阶段安排

### 第一阶段：核心模型升级

目标：完成命名空间模型、Key 设计、接口模型设计。

任务：

1. 设计新的 Etcd Key 结构
2. 设计 namespace 配置模型
3. 调整发布、查询、版本接口的数据结构
4. 设计兼容当前实现的迁移方案

产出：

- 命名空间 Key 设计文档
- 接口模型文档
- Day1 设计结论

### 第二阶段：服务端能力补齐

目标：在现有服务端上补齐轻量 Apollo 核心服务能力。

任务：

1. 改造发布接口
2. 改造查询接口
3. 改造历史版本接口
4. 新增 diff 接口
5. 完善删除策略
6. 为审计日志预留模型
7. 升级 watch 维度到 namespace

产出：

- 更新后的服务端接口
- 测试用例
- 文档同步更新

### 第三阶段：SDK 增强

目标：将 SDK 从“能用”升级到“更稳定、可演示、可容错”。

任务：

1. 增加 namespace 支持
2. 增加本地缓存
3. 支持本地缓存回退
4. 支持多 namespace 聚合
5. 增加 typed API

产出：

- 新版 SDK
- demo 更新
- SDK 使用文档

### 第四阶段：控制台与演示能力

目标：补齐最小管理体验与项目展示能力。

任务：

1. 设计最小控制台页面
2. 提供发布、查询、回滚、版本对比页面
3. 整理部署脚本和演示脚本
4. 完善 README 和答辩材料

产出：

- 最小控制台
- 演示脚本
- 完整文档

## 6. 优先级划分

### P0 必做

1. namespace 模型落地
2. 新 Key 设计
3. 发布与查询接口升级
4. 版本接口升级
5. SDK namespace 支持
6. Day1 到 Day3 主链路跑通

### P1 应做

1. diff 能力
2. 删除策略完善
3. 审计日志预留
4. SDK 本地缓存增强
5. 控制台基础页面

### P2 可选

1. 灰度发布
2. 权限控制
3. 多实例事件同步优化
4. 更完整的文本配置格式支持

## 7. 验收标准

验收时至少满足以下条件：

1. 支持按 `app + env + namespace` 发布配置
2. 支持按 namespace 查询当前生效配置
3. 支持查看某 namespace 的版本历史
4. 支持回滚并生成新版本
5. 支持客户端监听 namespace 配置变更
6. SDK 能在主演示流程中稳定工作
7. 文档、接口和实现保持一致

## 8. 风险与注意事项

1. Key 结构升级会影响现有接口和数据，必须优先定稿。
2. 当前 `WatchManager` 是单机内存通知，未来多实例部署需要升级。
3. 发布过程目前不是事务性写入，后续需关注部分写入失败风险。
4. SDK 若无本地缓存，服务端不可用时客户端体验较差。
5. 如果接口先不统一，后续控制台接入成本会明显上升。

3. 新版 API 模型草案
4. Day1 设计结论文档
