# Agent 升级计划

本文档用于规划 GoLiteConfig 在当前配置中心基础上的 Agent 化升级方向。目标不是一次性引入复杂的多智能体系统，而是在现有发布、查询、版本管理、回滚、Watch、SDK、demo 链路之上，增加几个职责明确、实现成本可控、展示效果明显的轻量 Agent。

## 1. 升级目标

当前系统已经具备以下核心能力：

1. 配置发布 `POST /api/config`
2. 当前配置查询 `GET /api/config`
3. 版本列表查询 `GET /api/config/versions`
4. 配置回滚 `POST /api/config/rollback`
5. 配置变更监听 `GET /api/watch`
6. Go SDK 本地缓存与热更新
7. demo-service 热更新演示

下一阶段的 Agent 升级目标：

1. 让系统具备“感知变化后自动处理”的能力
2. 在配置发布和回滚链路中引入自动化判断
3. 提升系统展示效果，使项目更像一个可扩展的智能配置中心

## 2. Agent 设计原则

升级遵循以下原则：

1. 优先做轻量 Agent，不引入复杂调度框架
2. 复用现有接口和数据结构，不重写主链路
3. 每个 Agent 职责单一，便于调试和演示
4. 先做规则型 Agent，再考虑接入更复杂的模型能力

## 3. 推荐升级方向

### 3.1 配置变更通知 Agent

职责：

1. 监听配置变化
2. 自动输出通知或推送消息
3. 记录变更摘要

可基于现有能力：

1. 服务端 `GET /api/watch`
2. SDK `Watch`
3. 版本信息和回滚信息

可实现的最小功能：

1. 监听到配置变化后打印变更摘要
2. 输出 `app/env/version/revision`
3. 输出变更的 key 和旧值、新值

后续扩展：

1. 推送到 Webhook
2. 推送到企业微信或钉钉
3. 记录审计日志文件

### 3.2 配置校验 Agent

职责：

1. 在发布前校验配置是否合法
2. 拦截高风险配置
3. 提供明确错误原因

可校验内容：

1. 必填项是否存在
2. 端口是否为数字
3. 地址格式是否合法
4. 生产环境是否允许修改敏感配置

建议落点：

1. 服务端 `Publish` 前增加校验逻辑
2. 或做成独立 `validator` 模块，由 `Publish` 调用

展示效果：

1. 发布非法配置时，系统能明确拒绝
2. 返回“哪个配置项有问题、为什么有问题”

### 3.3 自动回滚 Agent

职责：

1. 发布后自动检测配置是否异常
2. 发现异常时自动调用回滚逻辑
3. 将回滚原因写入 comment

最小实现建议：

1. 使用规则判断某些配置是否合法
2. 如果检测失败，自动回滚到上一个稳定版本
3. 输出“检测失败 -> 自动回滚”的日志

建议演示流程：

1. 发布正常版本
2. 发布一个带非法值的新版本
3. Agent 检测异常
4. Agent 自动回滚
5. demo-service 自动恢复

这个方向最适合展示“系统具备自愈能力”。

### 3.4 配置解释 Agent

职责：

1. 自动把配置差异转成自然语言说明
2. 帮助开发者理解某次变更的影响

最小实现建议：

1. 基于固定规则模板生成解释
2. 对关键 key 输出固定说明

示例：

```text
database.host 从 127.0.0.1 变为 192.168.1.10
解释：数据库地址从本地切换到远程内网地址，业务服务将尝试连接远程数据库。
```

适合后续作为展示增强项。

### 3.5 版本差异分析 Agent

职责：

1. 对比两个版本的配置差异
2. 生成新增、删除、修改摘要

最小实现建议：

1. 输入两个版本号
2. 输出新增 key、删除 key、修改 key
3. 输出变更摘要说明

这个方向可以与后续 `diff` 接口结合。

### 3.6 SDK 本地恢复 Agent

职责：

1. 在配置中心短暂不可用时进入降级模式
2. 继续使用本地缓存提供配置
3. 在服务恢复后自动重新同步

建议升级点：

1. SDK Watch 失败时输出降级日志
2. SDK 在降级期间仍提供 `Get`
3. 配置中心恢复后自动退出降级状态

这个方向更偏工程稳定性增强。

## 4. 优先级建议

结合当前项目状态，推荐优先级如下：

### P0：优先实现

1. 配置变更通知 Agent
2. 配置校验 Agent
3. 自动回滚 Agent

原因：

1. 可直接复用当前发布、Watch、回滚链路
2. 展示效果明显
3. 实现复杂度可控

### P1：第二阶段实现

1. 版本差异分析 Agent
2. SDK 本地恢复 Agent

### P2：展示增强项

1. 配置解释 Agent

## 5. 推荐实施顺序

### 第一步：配置校验 Agent

先做原因：

1. 最容易落地
2. 可以直接增强 `Publish`
3. 能快速提升系统可靠性

建议实现位置：

1. `internal/service/config_service.go`
2. 独立拆分到 `internal/service/validator.go`

### 第二步：配置变更通知 Agent

先做原因：

1. 当前 Watch 链路已经成熟
2. demo-service 也已经能观察变化
3. 很容易做出可见效果

建议实现位置：

1. 服务端 Watch 基础上增加通知逻辑
2. 或在 `examples` 下增加专门的通知演示程序

### 第三步：自动回滚 Agent

先做原因：

1. 当前回滚能力已经稳定
2. 可以与校验 Agent 联动
3. 很适合做系统亮点演示

建议实现位置：

1. `internal/service/rollback_agent.go`
2. 或先在 demo 流程中做规则版自动回滚

## 6. 最推荐的组合方案

如果时间有限，最推荐实现这一套：

1. 配置校验 Agent
2. 自动回滚 Agent

推荐展示流程：

1. 发布一个正常版本
2. demo-service 正常热更新
3. 发布一个非法配置版本
4. 校验 Agent 检测失败
5. 自动回滚 Agent 回滚到上一个稳定版本
6. demo-service 自动恢复

这个组合最能体现：

1. 配置中心具备风险识别能力
2. 配置中心具备自愈能力
3. 版本管理、回滚、Watch、SDK、demo 已形成完整闭环

## 7. 后续文件建议

如果开始实现 Agent，可考虑新增以下文件：

```text
internal/service/validator.go
internal/service/notify_agent.go
internal/service/rollback_agent.go
internal/service/diff_agent.go
examples/agent-demo/main.go
```

## 8. 结论

GoLiteConfig 当前已经具备升级为“轻量智能配置中心”的基础。下一阶段不建议直接引入复杂大模型编排，而应优先围绕现有主链路增加轻量 Agent，重点突出：

1. 自动感知变化
2. 自动校验风险
3. 自动回滚恢复

其中最值得优先实现的是：

1. 配置校验 Agent
2. 自动回滚 Agent

这两者结合后，将显著提升项目的完整度、可展示性和工程价值。
